# SceneSearch API contract

**Status:** frozen for the frontend. Breaking changes get a new path (`/api/v2/...`), never a
silent edit. Source of truth for the shapes is `src/models/schemas.py`; this document explains the
*why*, which the schema cannot.

Base URL (local): `http://localhost:8000` · Deployed: _TBD — Hugging Face Space, added on first deploy_

Interactive docs are generated by FastAPI at `/docs` once the service runs.

---

## What this service does

Natural-language search over a corpus of driving-footage keyframes. The engineer types the scenario
they need ("a pedestrian to the front-left"); the service returns candidate frames, **or tells them
the archive does not contain it**.

That second half is not a nicety. Ten confident wrong frames cost more than an empty result,
because the engineer has to watch them to find out they are wrong. Rejection is a measured
component, not an afterthought — see `experiments/M2_DESIGN.md` §6.1.

Corpus for the demo: **6,858 CAM_FRONT keyframes over 170 scenes**, from nuScenes `v1.0-trainval`
parts 9 and 10 (Boston + Singapore, 2018). This replaced the 404-frame `v1.0-mini` corpus on
2026-08-02; nothing in the contract changed with it, but every count below did.

## `GET /health`

Liveness. Must stay working — the deploy and the grading rubric both depend on it.

```json
{ "status": "ok", "version": "0.1.0", "corpus_frames": 6858 }
```

## `GET /api/v1/status`

Readiness, which is different from liveness: the process answers `/health` before the embeddings
and index have finished loading.

```json
{ "status": "ready", "artifacts_loaded": true, "encoder": "openclip:ViT-B-16-SigLIP2:webli" }
```

Plus `corpus_frames`, the full `provenance`, and `rejection_band` — whether the band this process
serves was fitted against the corpus it loaded:

```json
{ "state": "fitted", "ok": true, "corpus": "27b334b33461", "fitted_for": "27b334b33461",
  "shipped": { "tau_reject": 0.3, "tau_confident": 0.5 },
  "reviewed": { "tau_reject": 0.3, "tau_confident": 0.5 },
  "fitted":   { "tau_reject": 0.3, "tau_confident": 0.57, "weakest_real": 0.33, "margin": 0.035 },
  "report": "eval/results/rejection_band_nuscenes.json", "detail": "…" }
```

| `state` | meaning |
|---|---|
| `fitted` | a fit is recorded for this corpus and `config.py` still carries the band it was reviewed against |
| `unfitted` | no fit recorded — the band was inherited from other footage (M2_DESIGN §10.3) |
| `corpus_mismatch` | the recorded fit is for a different corpus than the one loaded |
| `config_drift` | `config.py`'s band has been edited since the fit was reviewed |

`shipped` and `fitted` differing is **not** a fault: `tau_confident` ships at 0.50 where the sweep
prefers 0.575, deliberately. Drift is measured against `reviewed`, not against `fitted`. Written by
`scripts/band/stamp_rejection_band.py`; read by `src/services/search/band.py`.

Also `temporal_density` and `source_clips` *(added 2026-08-27)* — how far apart this corpus's frames
sit in time, and whether it can name the footage they came from:

```json
{ "temporal_density": { "median_gap_s": 0.5, "p90_gap_s": 0.501, "max_gap_s": 0.751,
                        "n_gaps": 6688, "is_dense": true, "strip_window_s": 3.0, "detail": "…" },
  "source_clips": 0 }
```

**Unlike the band, this is derived rather than stamped, and that is deliberate.** A band cannot be
recomputed at startup — fitting one needs a judgment set and a captioner — so it is recorded and
read back, and `corpus_mismatch` exists because the record can outlive the corpus. Density is the
frames' own timestamps: re-deriving it costs one pass, so there is nothing to stamp, nothing to
backfill and no state in which the number disagrees with the corpus underneath it.

`is_dense` answers exactly one question — can `/frames/{id}/context`'s default 3 s window hold two
frames at this spacing — so the cut is `strip_window_s / 2`, not a chosen constant. The served
corpus reports **0.50 s, dense**; the staged Hanoi corpus reports **5.00 s, sparse**. `source_clips`
is 0 wherever the corpus kept no source video, which on nuScenes is permanent.

## `POST /api/v1/search`

The primary endpoint.

**Request**

```json
{ "query": "a pedestrian to the front-left" }
```

| field | type | notes |
|---|---|---|
| `query` | string, 1–500 | empty or over-length → **422**, from Pydantic validation |
| `top_k` | int, 1–50, **optional** | defaults to the server's `DEFAULT_TOP_K` (10 as shipped). Also the diversity window — see note below |

**`top_k` is optional and the frontend does not send it** (changed 2026-08-28). It was `10` written
four times — the schema, two graph nodes and `FE/src/api/client.ts` — for a number that is a measured
retrieval parameter, not a display preference. It now lives once, in `config.py: default_top_k`, so a
box can change it in `.env` and both entry points into the graph follow. Send it explicitly only when
you want something other than what the service was tuned for.

**Response `200`**

```json
{
  "matched": true,
  "confidence": "high",
  "reason": null,
  "constraint": {
    "objects": ["pedestrian"],
    "relations": { "pedestrian": ["front_left"] },
    "attributes": {},
    "scene": {},
    "out_of_scope": null,
    "unsupported_relation": null,
    "query_en": "a pedestrian to the front-left"
  },
  "results": [
    {
      "frame_id": "e93e98b63d3b40209056d129dc53ceee_CAM_FRONT",
      "scene_id": "cc8c0bf57f984915a77078b10eb33198",
      "timestamp_s": 12.4,
      "score": 0.312,
      "match_probability": 0.85,
      "thumb_url": "/api/v1/frames/e93e98b63d3b40209056d129dc53ceee_CAM_FRONT/thumb",
      "satisfied": ["object:pedestrian", "rel:pedestrian:front_left"],
      "source": null,
      "moment": null
    }
  ],
  "distinct_scenes": 6,
  "trace_id": "9f2c…"
}
```

### Three outcomes, not two — `matched` + `confidence`

| `matched` | `confidence` | `results` | what it means | render as |
|---|---|---|---|---|
| `true` | `"high"` | populated | the archive contains this | results, no banner |
| `true` | `"low"` | **populated** | closest frames found, but a check against their descriptions could not confirm the match | results **plus** the `reason` as a caveat banner |
| `false` | `null` | `[]` | nothing here matches | empty state, showing `reason` |

**The `low` case must show its results.** It is tempting to treat "low confidence" as "no match" and
render the empty state — please don't. That is the exact failure the band exists to remove.

The two errors are not symmetric. A wrongly shown result is **self-correcting**: the user looks,
sees it is wrong, and rephrases. A wrongly hidden one is **invisible and final**: they are told the
archive lacks footage it actually holds, and nothing in the interface suggests otherwise. Measured on
the benchmark, a single cutoff hid about a quarter of legitimate searches — including *"a pedestrian
to the front-left"*, which is one of the queries this system handles best. The shipped band refuses
**0%** of real queries and still refuses 13% of empty ones outright; the rest land in `low`.

**`matched: false` is a first-class outcome, not an error.** It still returns `200`, with an empty
`results` array and a `reason` in plain English. Render it as an answer ("this archive has no snowy
footage"), not as a failure. Test against `{"query": "a bus on fire"}` — buses are common in the
corpus and fires are absent, so it is refused outright rather than merely flagged.

**`constraint` is what the parser understood.** An LLM turns the sentence into a structured filter
and it will sometimes be wrong. Showing the interpretation makes a wrong parse recoverable; hiding
it means the user silently gets the wrong search. Displaying it as editable chips would be ideal,
read-only is acceptable.

**`constraint.out_of_scope`** is set when the query asks for something a single frame cannot answer
— motion over time, like *"a vehicle cutting into our lane"* or *"the ego vehicle braking hard"*.
The retrieval unit is one frame, so no amount of model quality reaches these. Engineers type these
queries, so the honest answer is a designed state rather than an accident.

**What that state is now depends on whether the corpus kept its source footage** *(changed
2026-08-27)*. It used to be a refusal unconditionally: `matched: false`, empty `results`. That is
still exactly what the **served nuScenes corpus** returns, and always will — its source blobs were
pruned after extraction, so there is nothing to offer instead. **A client must keep handling it.**

On a corpus whose `videos.json` names its clips — the staged Hanoi corpus does — the query is
retrieved for normally and the answer is the closest moments *with a link into the footage*, plus a
`reason` that says the movement itself is unconfirmed. **The claim gets weaker, not stronger**: the
product still never asserts it saw the manoeuvre. The rejection band is untouched and still decides
whether anything matched at all, which is what stops this becoming "ten confident frames for a
question we cannot answer". Measured on Hanoi, the six motion queries score **0.3501–0.5076** against
`tau_reject` 0.30 — above the floor, mostly `low` — so the gate is doing the work rather than being
bypassed (`eval/results/temporal_source_hanoi.json`).

**That run measured Hanoi alone (2,211 frames) and reported `link_coverage: 1.0`. Do not quote that
figure for the deployed corpus.** On the 9,069-frame merge a query draws from both, and nuScenes hits
carry `source: null`, so coverage is per-query: `a motorbike in the rain` links **10/10**, `a car
overtaking on the right` **6/10**, and `a bus pulling out from the kerb` **0/10** — nuScenes has
1,243 bus frames to Hanoi's 514 and takes every slot. Motorbike-, rain- and Hanoi-street-shaped
queries link reliably; car, bus and pedestrian ones often do not. Measured on the live box
2026-08-31.

So `out_of_scope` set means "no single frame settles this", **not** "there are no results". Read
`matched` for that, as with every other query.

### `results[].source` — the footage behind the frame [added 2026-08-27]

`null` on the served corpus and always will be. Present only where the corpus's own `videos.json`
records which clip each frame came from:

```json
"source": {
  "url": "https://www.youtube.com/watch?v=cgosbZZmns4&t=257",
  "title": "Hà Nội ơi (195) Mưa",
  "uploader": "Hong Xuan",
  "license": "Creative Commons Attribution license (reuse allowed)"
}
```

- **`url` already carries the timestamp.** Built from the clip's page plus the frame's own
  `timestamp_s`; do not append your own seek parameter and do not reconstruct the URL.
- **It leaves the product.** Render it as *"see the source"*, not as a result — `target="_blank"`,
  `rel="noopener"`. It can also rot: a video may be deleted or made private, where a redacted frame
  cannot. Treat a dead link as a dead link, not as a bug in search.
- **`uploader` and `license` are a licence condition, not decoration.** The Hanoi clips are CC BY,
  which requires crediting the author. A renderer that shows the link and drops the credit breaks
  the licence — so if there is no room for the credit, there is no room for the link.
- **Nothing is re-hosted, deliberately.** The source clips are unredacted street video, faces and
  plates intact; this project publishes redacted frames and must not become the publisher of the
  footage they came from. A pointer is also the better answer: public, verifiable by anyone, free to
  store, and real motion at the clip's own frame rate rather than 2 Hz stills.

### `results[].moment` — a redacted clip this service holds [added 2026-08-28]

The other half of `source`, and **null on almost every result**: clips are cut for a handful of
frames, not for the corpus. ~~No deployed box has any.~~ **Production has served ten since the merge
mount landed** — `MOMENTS_DIR` points at `/opt/scenesearch/merged/moments`, so `GET /moments` returns
10 and a hit can carry one. Verified 2026-08-31. Still rare per result: at the default `top_k` of 10
only `a motorbike cutting into our lane` surfaces one.

```json
"moment": {
  "id": "m05",
  "video_url": "/api/v1/moments/m05/video",
  "closest_m": 5.0,
  "events": [[5.7, 7.7, "overtake"], [7.7, 9.7, "cut_in"]]
}
```

- **Offer both when both are present.** The clip is footage this project owns and redacted; the
  deep link is the unmodified original and is what makes the claim checkable. Neither replaces the
  other.
- **`video_url` is a byte-range mp4 on this service** — prefix it with the API base and hand it to a
  `<video>` element. It streams from local disk and never redirects off-site.
- **`events` are a person's reading of the footage, not a detection.** `[start_s, end_s, label]` in
  seconds from the start of the clip, hand-labelled during review. Rendering them as something the
  system found would be the one claim this product must never make — label them as human.
- A clip appears here only if it passed the build's own privacy scan; a manifest that failed does
  not load at all, so the field cannot surface an uncertified clip.

### `constraint.unsupported_relation` — the part of the query that was not searched for [added 2026-08-12]

**When this is set, the answer is to a narrower question than the one asked.** `reason` already says
so in plain English, so a client that renders `reason` needs no extra work — but do not swallow both.

The position vocabulary places an object **in the frame** (`front`, `front_left`, `front_right`). It
cannot place an object **against another object**. So *"a motorbike to the right of a bus"* is parsed
as `motorcycle` + `bus` with no position on either, and searched as "a frame containing both, in any
arrangement".

That was always the behaviour. What changed is that it used to be **silent**: the response was
indistinguishable from a correct answer to the question actually asked. `relax_node` reports the
widenings it performs during a search; this discard happens at parse time and reached nobody.

```json
"constraint": { "objects": ["motorcycle", "bus"], "relations": {},
                "unsupported_relation": "to the right of a bus" }
```

```
reason: "... One part of that query was not searched for: 'to the right of a bus' places one object
         relative to another, and this archive only records where something sits in the frame.
         These are frames containing the objects you named, in any arrangement."
```

It is **not** a filterable condition and never becomes one — `metadata_constraint` ignores it.
It appears on refusals too, and matters more there: without it a user reads "nothing matches" and
rephrases the half that was already working.

### Queries may be written in any language [added 2026-08-12]

**Vietnamese works, and so does English. Nothing in the client needs to detect or declare a
language.** Before this the API accepted a Vietnamese query, parsed it correctly, and then refused it
— `matched: false` on every single one, regardless of what the archive held (issue #70).

The parse step was never the problem: `gpt-4o-mini` read Vietnamese correctly and returned the right
objects, relations and scene tags every time. The refusal came from the rejection gate, which scores
the query against the retrieved frames' English captions using an **English-only** sentence encoder.
Vietnamese landed at 0.057–0.123 where the same query in English scored 0.145–0.707 — under
`tau_reject` in every case, and with no relevance signal left in it, so no threshold could have
separated a real query from an empty one.

**`constraint.query_en` is the query in English**, and it is what the gate now scores. When the query
was already English it is that query **verbatim** — the band was calibrated on this encoder's score
distribution over English text, so a rephrase would move every English score off the distribution the
thresholds were fitted to. It is produced by the parse call that already runs, so it costs no extra
latency, no extra model, and no re-embedding of the caption vectors.

**Retrieval is not translated, deliberately.** SigLIP2's text tower is trained on multilingual WebLI
and reads Vietnamese directly: over 8 matched pairs, the fraction of the top-10 whose *detected*
metadata contained the queried object was **0.750 English against 0.787 Vietnamese**, with the `night`
tag at 1.00 in both. The two rankings overlap only 0.275 at k=10 — different frames, equal quality.
Feeding a translation into retrieval would discard a working multilingual encoder to gain nothing.

A consequence worth expecting rather than reporting as a bug: a query and its translation return
**different frames and slightly different scores**, because retrieval still runs on what was typed.
Only the gate is normalised.

`query_en` is null when the parser failed, in which case the gate falls back to the raw query.

### `score` is not a percentage — `match_probability` is [added 2026-08-05]

**Render `match_probability`. Never render `score * 100`.** Added, not changed: `score` keeps its
meaning and its place, so nothing that reads it breaks.

`score` is a raw SigLIP2 cosine, and the scale does not reach 1. Measured across all 6,858 frames:

| query | corpus min | median | corpus max | best frame as `score * 100` | as `match_probability` |
|---|---|---|---|---|---|
| `a wet road at night` | — | — | 0.171 | 17.1% | **92.1%** |
| `pedestrian in the rain` | 0.009 | 0.067 | 0.164 | 16.4% | **85.0%** |
| `a submarine at the intersection` | 0.026 | 0.088 | 0.134 | 13.4% | **15.9%** |
| `asdfghjkl qwerty zxcvbn` | 0.050 | 0.065 | 0.091 | 9.1% | **0.1%** |

The best-matching frame in the entire archive scores about 0.17, and meaningless input still scores
0.09 — so the old display showed a perfect match as "16%", could never fill a bar, and put nonsense
only seven points below a correct answer. The band also **moves per query**, which is why two raw
scores from different searches cannot be compared at all.

SigLIP2 trains with a **sigmoid** loss: the cosine is the input to a learned affine transform, and
both parameters ship inside the checkpoint (`logit_scale` 112.67, `logit_bias` −16.77 for
`ViT-B-16-SigLIP2:webli`). `match_probability` is `sigmoid(scale · cos + bias)` — the number the
model was fitted to emit. It is read from the loaded encoder, never hardcoded, so swapping the
encoder cannot leave a stale constant behind. The transform is strictly monotonic, so **ranking is
identical** and no retrieval metric moves.

**It measures the embedding alone, and this matters more than it sounds.** `a car to the
front-right` returns frames whose `satisfied` array confirms `rel:car:front_right` — the metadata
filter working exactly as designed, and the project's strongest measured result (+0.040 → +0.359) —
while `match_probability` reads **~2%**. That is not a bug in either number: the embedding genuinely
cannot see position, which is *why* the filter exists. For relational queries, **`satisfied` is the
evidence and the percentage is not**. A UI that shows the number without the chips will misrepresent
its best feature.

`null` means the backend has no encoder loaded. Show the raw `score` and no bar; do not synthesise a
percentage.

### `distinct_scenes`

Keyframes are sampled at 2 Hz, so consecutive frames are nearly identical and a naive top-10 can be
ten frames of the same five seconds. The service caps results per source clip to prevent that;
`distinct_scenes` reports how many distinct clips the results actually span, so the UI can surface
variety. With 170 clips in the corpus the ceiling is effectively `top_k`; measured at `top_k=10` it
runs **6.75–7.50** depending on the query tier, against 4.13–4.67 with the cap off.

### `top_k` doubles as the diversity window

Set it to the number of results you actually display. Measured (M2_DESIGN §7): applying the scene
cap beyond the displayed head costs two-thirds of the ranking quality and buys **no** additional
diversity, because a metric at rank 10 cannot see past rank 10.

This is why the parameter is **not** a page size and why raising `DEFAULT_TOP_K` is not free: at cap
2, relational lift measures **+0.113 at window 10 against +0.077 at window 50**, while
distinct-scenes@10 is 5.50 either way. A box set above 10 returns a longer page at lower precision
and is no longer described by any figure in `eval/results/`, all of which were measured at 10.

## `GET /api/v1/frames/{frame_id}/thumb`

Returns `image/jpeg`. Width is fixed at **ingest**, not per request — the API serves whatever bytes
are on disk and never resizes. One number for every writer, `scripts/anonymise.py: THUMB_WIDTH`,
currently **640**. The corpus published before 2026-08-05 was built at 320 and stays that width until
it is regenerated, so do not assume a size: use the image's own dimensions.

Not purely cosmetic, which is why it is stated here — deferred captioning reads this same thumbnail
at query time (`src/services/search/captions.py`), so the width feeds caption quality and therefore
the rejection band.

Cacheable and immutable — `frame_id` is stable, so the response carries a long `Cache-Control`.
Unknown id → `404`.

Use the `thumb_url` from the search response rather than building the path yourself.

**Faces and licence plates are redacted**, mosaicked at source resolution during ingest
(`scripts/anonymise.py`) so no file on disk holds the original pixels. This is the only image the
API serves — grid and detail modal both use it — so there is no unredacted path to reach. As
certified on 2026-08-05: **5,511 regions over 2,616 of the 6,858 frames (38.1%)** — dedicated
face/plate detectors (YOLO11n, 0.35 floor) unioned with the top 28% of every `person` box, which
supplies 89% of the redacted area. Coverage is the union of two detector recalls, so it is a
mitigation rather than a guarantee; `data/artifacts/provenance.json` names the exact weights and
`docs/reference/assets-dataset-card.md` states the limits. **After regenerating thumbnails, republish `thumbs.tar`** or a deployment keeps serving
the previous, unredacted set (`docs/deploy.md`).

## `GET /api/v1/frames/{frame_id}/context` *(added 2026-08-22)*

A **keyframe strip**: the frames leading up to one hit, so a still can be judged as a **moment**. A single keyframe cannot
show motion — a pedestrian stepping into the road and one standing still look identical — and this
is what lets a user tell them apart.

`?before=` seconds of lead-in, default **3.0**, range 0.5–10.0. Outside that range → `422`. Unknown
or malformed id → `404`, same posture as the thumb route.

```json
{
  "frame_id": "5ba77c6f…_CAM_FRONT", "scene_id": "65cfdc10…", "timestamp_s": 4.05,
  "requested_before_s": 3.0, "complete": true,
  "mode": "strip", "median_gap_s": 0.5, "source": null,
  "frames": [
    {"frame_id": "234bb362…_CAM_FRONT", "timestamp_s": 1.00, "offset_s": -3.05, "thumb_url": "/api/v1/frames/234bb362…_CAM_FRONT/thumb"},
    {"frame_id": "5ba77c6f…_CAM_FRONT", "timestamp_s": 4.05, "offset_s":  0.00, "thumb_url": "/api/v1/frames/5ba77c6f…_CAM_FRONT/thumb"}
  ]
}
```

Five things the client must know:

- **Ascending by time, and the anchor is the last element**, at `offset_s` exactly `0.0`. Render the
  strip in the order given. Use `offset_s`, not a difference of `timestamp_s` — that field is an
  offset into its own clip and is not comparable across scenes.
- **`complete: false` means the scene did not reach back that far**, not that something failed.
  nuScenes scenes run ~20 s, so a hit near the start has less history than was asked for; **2.5% of
  the corpus has no predecessor at all** and returns the anchor alone. Label it — a silently short
  strip reads as a bug.
- **It never crosses a scene boundary.** Two scenes are unrelated moments, often a different street
  on a different day; splicing them would look like continuous footage and would not be.
- **`mode` says whether you actually got a strip** *(added 2026-08-27)*. `"sparse"` means the window
  returned the anchor and nothing useful before it, because this corpus's frames are too far apart —
  **render `source` instead and never present one still as a moment**, which is the whole defect this
  field exists to stop. It is decided from what the window returned, not from a corpus-wide label, so
  it is right per frame even where spacing is not uniform. **`complete` and `mode` are different
  claims**: `complete: false` says this scene ran out of history, `sparse` says the corpus never had
  the resolution. A scene opener on a dense corpus is both. `median_gap_s` is there so a client can
  say *why* — 0.50 s on nuScenes, 5.00 s on staged Hanoi, where a 3 s window is the anchor alone
  about 83% of the time.
- **It is a strip of stills, not a clip.** Motion-over-time queries ("cutting in", "braking") are
  never *answered* by this route: one frame cannot show motion and neither can seven of them at
  2 Hz. Do not present this strip as evidence that such a query was satisfied. On the served corpus
  those queries are still refused outright with `out_of_scope`; where a corpus keeps its source
  footage the answer is `results[].source`, which is video, not this. **The strip is also not
  portable across corpora** — it assumes ~0.5 s spacing, and on a 5 s-gap corpus a ±3 s window
  returns the anchor alone 83% of the time, i.e. the frame already shown, relabelled as a moment.
  Nothing in an artifact records a corpus's sampling density yet, so nothing would say so.

**"Strip", not "clip", and the distinction is reserved deliberately.** These are the corpus's own keyframes at 2 Hz — roughly 7 stills for 3 seconds — not video cut from source footage. A real clip endpoint would be a separate route returning `video/mp4`, resolved from wherever the operator's footage actually lives, and it carries privacy costs this route does not: source video is unredacted, and a 3-second cut at 60 fps is 180 frames rather than 7. See `docs/tasks/task-source-resolver-and-clips.md`. Do not describe this endpoint as returning a clip.

**It publishes nothing new.** Every frame returned is already in the served corpus and already
redacted — `Corpus` carries `scene_of` and `timestamp_of`, so this reads what is loaded. The images
come from the same `/thumb` route with the same path-traversal check, so the privacy gate and the
security surface are unchanged. Frames sit ~0.5 s apart (2 Hz), so a 3 s window is ~7 images;
**73.7%** of the corpus can supply a full 3 s, 90.1% can supply 2 s, 97.5% has at least one.

## Moment clips — `/api/v1/moments` *(added 2026-08-27)*

Redacted six-second cuts held on local disk: the **private-storage** case, where the pixels are ours
so the product can show the motion instead of pointing at someone else's video. `results[].source`
and this are the two halves of one answer — the deep link is the unmodified original and is the
evidence; the clip is redacted, ours, and playable in the page.

`GET /api/v1/moments` lists what this service holds, `GET /api/v1/moments/{id}` returns one **with
the vehicles tracked through it**, and `GET /api/v1/moments/{id}/video` streams the mp4.

```json
[{ "id": "m01", "video_id": "clip06_hanoi", "query": "a motorbike cutting into our lane",
   "keyframe_timestamp_s": 107.107, "window_s": [103.107, 109.107], "fps": 10,
   "video_url": "/api/v1/moments/m01/video",
   "deep_link": "https://www.youtube.com/watch?v=bd9YW84zLmE&t=107" }]
```

- **An empty list is a normal answer, but no longer the only one.** This said "no deployed box has
  these clips and none is meant to". Production has served **ten** since the merged corpus was mounted
  — they ride in on `MOMENTS_DIR`, not on the image, so a box without that mount still returns `[]`.
  Both are valid states and the frontend must handle each: `[]` is not an error, and a non-empty list
  is not a promise that any given hit has one.
- **`events` is empty and `duration_s` is null on every clip production serves** (checked
  2026-08-31). The hand labels were never populated on the deployed set, so anything rendering an
  event list gets nothing. Do not build a demo around them.
- **`query` is what was searched for, not a finding.** Nothing has verified that the manoeuvre
  occurs in the clip, and the corpus has no annotations that could. Do not label a clip "cut-in".
- **The video route serves byte ranges**, so a `<video>` element can seek. `FileResponse` handles
  `Range` itself; the route does not parse one, which is deliberate — a hand-rolled range parser is
  a way to read past the end of a file. Ids are looked up in the manifest rather than joined onto a
  path, same posture as `/thumb`, and an unknown id is `404`.
### `GET /api/v1/moments/{id}` — one clip, with what was measured in it *(added 2026-08-28)*

```json
{ "id": "m02", "video_id": "clip15_hanoi", "fps": 10, "camera_h_m": 0.92,
  "video_url": "/api/v1/moments/m02/video",
  "tracks": [{ "label": "motorcycle", "closest_m": 2.8, "lateral_m": 0.08, "closest_at": 7,
               "distances": [4.8, 4.1, 2.8], "ground_plane_m": 2.6,
               "frames": [12, 33], "at": [12, 13, 15],
               "boxes": [[0.30, 0.50, 0.40, 0.70], [0.32, 0.50, 0.42, 0.72], [0.36, 0.50, 0.46, 0.76]] }] }
```

- **Separate from the list because the boxes are bulky** — six tracks over sixty frames is a few
  hundred rectangles. A page listing ten clips does not want them; a player opening one does. The
  headline number rides the search hit as `moment.closest_m`, so a card can say how close the nearest
  vehicle came without this request at all.
- **`closest_m` is a measurement and never a manoeuvre label.** Eight trajectory rules were scored
  against a hand-labelled gold and none could tell a cut-in from an overtake on this footage (best
  AUC 0.827, a ranking rather than a decision), so the product reports the distance it can support
  and stays silent on the label it cannot. Do not render it as "cut-in".
- **Draw `distances[i]`, never `closest_m`, on a moving box.** `closest_m` is the minimum over the
  whole clip and belongs on a summary line. It was on the tag first, and watching it play showed why
  that is wrong: an overtaking car held its closest value long after it had gone, and two vehicles at
  obviously different depths displayed the same figure. `distances` is aligned with `at`, one per box.
- **The distance comes from apparent size**: `focal * typical_height_for_class / box_height_px`,
  which needs **no horizon and no camera height** — only the declared `hfov_deg`. Render it with a
  `~`: the class-typical height is an assumption about the vehicle in the box, not a measurement of
  it. Two limits worth stating in any UI that shows it: it measures **to the camera**, not to the
  front of the car, and a vehicle so close that its box is **cut off by the frame edge** measures
  shorter than it is, so it reads further away than it is.
- **`ground_plane_m` is the road-plane estimate, kept for comparison and NOT for display.** On this
  footage it compresses everything into one band — on `m17` a car, a bus and two trucks at plainly
  different depths all read ~2.6 m, where apparent size spreads the same tracks over 4.1-22.6 m. Two
  causes: the per-window horizon regression can fail (it fell back to the 0.5 default on `m17`), and
  in dense traffic every box bottom sits at 0.79-0.96 of the frame, so `(y_bottom - horizon)` is a
  small noisy difference for near and far alike. `camera_h_m` is published for the same reason —
  on `clip15` it came back **0.92 m** where a dashcam sits nearer 1.3.
- **`lateral_m` is the sideways half of that road-plane figure**, kept because the Tier 3 ranking
  used it, where only within-window comparisons mattered. Not the displayed number.
- **`at` can have gaps, and a gap means draw nothing.** A missing frame is one the detector lost;
  interpolating a box across it would put a confident rectangle on footage that never supported one.
  `boxes` are fractions of the frame, so an overlay scales with the player rather than the encode.
- **`tracks: []` is not "nothing came near."** It is a manifest built before
  `scripts/moments/annotate_moment_tracks.py` ran. Absent measurement and measured absence are different
  claims and the UI must not merge them.

- **A clip that failed its own privacy check is not served at all.** The build decodes the mp4 it
  produced and re-runs the face and plate detectors **on the output**, because a claim about the
  frames that went into an encoder is not a claim about the file that came out. On failure it writes
  `verified: false`; the loader then refuses the whole manifest, so the refusal survives someone
  pointing a server at the directory anyway. This matters because `verify_privacy_assets.py` does
  not open mp4 and reports green on a tree full of video.

## Human review — `/api/v1/reviews`

The Brief asks for human-in-the-loop: an engineer confirms results before they become a dataset.
Search cannot make that claim on its own — `report.md` §2 measures `a wet road at night` at P@10
0.10, so some returned frames are always wrong. These endpoints record the confirmations, and
`/reviews/export` produces the artifact.

**A verdict is keyed on the triple `(query, frame_id, reviewer)`, never on the frame alone.** A frame
is a positive *for a question someone asked*, judged *by someone*: the same frame is a correct hit
for `driving at night` and a wrong one for `a cyclist at night`. Keying on the frame would make the
second verdict silently overwrite the first, and it is also the shape a retrieval test set needs —
query → judged positives.

**`reviewer` is part of the key, and it is why the triple is a triple** *(added 2026-08-08)*. One deployment
serves every tester from one table. Without it, two people judging the same frame for the same query
collided on the primary key and the upsert destroyed the first verdict with no trace — and
disagreement between raters is the most informative thing a multi-rater session produces. `GET
/reviews` was also unscoped, so the second tester opened a query already marked up by the first and
judged against someone else's answers.

**Who that reviewer is: the account when there is a session, the browser when there is not**
*(changed 2026-08-30)*. A signed-in caller's verdicts are filed under `user:<user_id>` and the
`reviewer` they sent is **ignored**, not merged; an anonymous caller keeps the pseudonymous UUID the
frontend generates into `localStorage` (`FE/src/lib/reviewer.ts`) and attaches in `api/client.ts`.

The browser id was right while the service had no accounts, and login is what stopped it being
right: `localStorage` belongs to a browser profile, so three accounts signing in on one laptop were
one reviewer — each seeing the others' ticks and crosses, which is the contamination the `reviewer`
column was added to prevent, arriving from the other side. Same shape as the `OPERATOR_TOKEN`
retirement on 2026-08-27: a mechanism correct for a service without accounts, left running after the
service got them.

Two consequences worth knowing. **A claim cannot impersonate an account** — both id spaces are
UUIDs, so an anonymous caller sending `user:<someone's id>` is refused with `400`, which matters
because `/reviews/export` publishes those ids by design and `DELETE /reviews` takes the same triple.
And **verdicts recorded before this are not rewritten**: they keep their browser ids, because
guessing which account a browser belonged to would invent attribution rather than recover it.

Send the **composed** query, the text actually searched with filters folded in, not the raw box
contents.

| method | path | body / params | notes |
|---|---|---|---|
| `PUT` | `/reviews` | `{query, frame_id, reviewer?, decision, note?}` | Upsert **per reviewer**. Re-deciding replaces your own verdict, never another's. `404` if the corpus has no such frame; `422` on an unknown `decision`; `400` when an anonymous caller sends no `reviewer` or claims the `user:` namespace |
| `DELETE` | `/reviews` | `?query=&frame_id=&reviewer=` | Undo, scoped to that reviewer. Idempotent — `204` even when there was nothing to undo. A signed-in caller can only undo their own: the id comes from the cookie, never the query string |
| `GET` | `/reviews` | `?query=&reviewer=` | **That reviewer's** verdicts for one query, so a repeat search restores them instead of losing them |
| `GET` | `/reviews/summary` | `?reviewer=` *(optional)* | `{approved, rejected, bookmarked, queries_reviewed, total, reviewers}`. **Sending `reviewer` asks for your own progress; omitting it asks for everyone's.** Your own is the account's when you are signed in — a tester should not be anchored by a shared count. Without it, the whole table. `reviewers` is always global |
| `GET` | `/reviews/export` | `?format=csv\|json&decision=approved\|rejected\|bookmarked\|all` | Download; sets `Content-Disposition: attachment`. Rows carry `reviewer`; JSON also lists `reviewers` at the top |

Verdicts recorded before 2026-08-08 are migrated automatically and attributed to
`unknown-pre-attribution` — a marker, not a person, and greppable in an export.

`decision` is one of `approved`, `rejected`, `bookmarked`. **`bookmarked` is not a weaker
`approved`** — it means "come back to this", so export defaults to `approved` only and a bookmark
never reaches a dataset by accident. Export `decision=all` when you want to *inspect* rejections
rather than train on them.

**JSON is the complete export; CSV is the spreadsheet convenience.** JSON carries the corpus
`provenance` — which archive, which encoder — because a list of frame ids is not a test set unless
it records what it indexes. CSV has nowhere structured to put that, and a comment header would break
naive parsers. Both carry `scene_id` and `timestamp_s` so a row locates its source clip.

**The database is a working buffer, not the deliverable.** It is stdlib sqlite at
`settings.database_url`, and the deployment target has an ephemeral filesystem: a container restart
loses unreviewed state. That is a deliberate trade rather than an oversight — the reviewer's output
is the export, and a managed database is not four weeks of work this project has. **Export before
you finish a session.**

## Authentication *(added 2026-08-21, `v1.6.1`)*

A JWT auth layer is mounted at `/api/v1/auth`, `/api/v1/users` and `/api/v1/admin`. **No product
route in this contract requires it** — `/search`, `/chat`, `/reviews`, `/frames` are all reachable
without a token, by design (the review path attributes verdicts to a pseudonymous browser id, not an
account). Auth exists for the operator-facing user and admin surface, and does not gate the product.

**It is not provisioned on the current deployment.** The box carries no auth secrets or database URL,
so `GET /api/v1/auth/me` returns `401` (gating works) but `POST /api/v1/auth/login` returns `500`
(no Postgres to reach). Treat auth as present in the codebase, not a working feature at the Live URL,
until the box `.env` sets `DATABASE_URL`, `JWT_SECRET_KEY` and the OAuth/SMTP values.

| method | path | who |
|---|---|---|
| `POST` | `/auth/register`, `/login`, `/refresh`, `/logout` | anyone; sets a refresh token in an httpOnly cookie |
| `POST` | `/auth/send-otp`, `/forgot-password`, `/reset-password` | anyone; email OTP, Redis-backed with an in-memory fallback |
| `POST` | `/auth/google` | anyone; Google OAuth 2.0 |
| `GET` | `/auth/me` | the signed-in user; `401` without a valid token |
| `GET`, `PATCH` | `/users/me`, `/users/me/password` | the signed-in user; mutations require the CSRF header |
| `GET`, `POST`, `PATCH`, `DELETE` | `/admin/users…`, `GET /admin/stats` | `Admin` role only (`require_role`), else `403` |

## Access and limits *(added 2026-08-12)*

Product routes have no accounts: the line is anyone with the URL, and the person running the
session. (The auth surface above is separate and gates none of them.) Two endpoints are on the
operator's side of that line.

| endpoint | who |
|---|---|
| `GET /reviews/export` | **signed in** — any account, no role |
| `GET /reviews/summary` **without** `reviewer` | **signed in** — this is the whole-table view |
| `GET /reviews/summary?reviewer=…` | anyone; a tester's own progress, and what the review bar calls |
| everything else | anyone with the URL |

Authority comes from the `access_token` cookie the login sets, and needs nothing in the URL. That is
worth spelling out because it used to: the gate was a shared `OPERATOR_TOKEN` accepted in an
`X-Operator-Token` header **or** a `token` query parameter, the query parameter existing only because
the export is reached by *navigating* to a link — `Content-Disposition: attachment`, so the browser
saves it under the server's filename — and a link cannot set a header. A link does send cookies:
`access_token` is `Path=/; SameSite=lax`, and a top-level GET is exactly what `lax` permits.

**No role is checked, deliberately.** The export is the engineer's own work product; requiring
`Admin` would put a permission request between a person and the dataset they just built, and most
accounts on the box are role `User`. `401` is therefore the only refusal — *sign in*.

**Why the export specifically.** `?decision=all` returns every `(query, frame_id, reviewer)` triple,
which is exactly what `DELETE /reviews` requires. An open export is not only a data leak; it hands
out the means to empty the table one call at a time. Gating it is what closes the delete path.

Frontend: the export controls render for any signed-in user (`ReviewBar.tsx`, `ExportData.tsx`). `lib/operator.ts`, which stored a token supplied once as `?operator_token=…`, was
deleted with the gate it served.

### Search history

**One list per account, server-side** *(moved off `localStorage` 2026-08-30)*. It used to be five
rows in browser storage, which is a browser profile rather than a person: invisible the moment an
engineer opened the product on a second machine, and shared by every account that signed in on one
laptop. A login over per-browser state does not separate people; it only makes the sharing harder to
notice. `src/services/history.py` carries the argument.

**Every route here requires a session**, unlike the review routes. Those are open because a
pseudonymous tester has to reach them from a link with no credential; a history has no such caller —
there is no useful anonymous version of "your recent searches". Whose history is being read or
written is never a request parameter.

| method | path | body / params | notes |
|---|---|---|---|
| `GET` | `/history` | — | This account's searches, newest first, capped at 50 |
| `POST` | `/history` | `{keyword, results_count?, filters?}` | `201`. Re-running a query moves it to the top rather than duplicating it — matched case-insensitively |
| `DELETE` | `/history/{entry_id}` | — | `204`; `404` when the row is not this account's, which covers "no such id" and "somebody else's" deliberately alike |
| `DELETE` | `/history` | — | Empty the list. Idempotent — clearing nothing is a `204` |

**Recording is a separate request from searching, on purpose.** Folding it into `POST /search`
would save a round trip and would couple the endpoint that must always work to a write that may
fail. A history row is a convenience and the search it describes has already succeeded, so the
frontend fires `POST /history` and does not wait for it (`rememberSearch` in `api/client.ts` never
throws). It would also make the open search endpoint write account data.

**Bounded, not archival.** Fifty rows per user, trimmed on write — and trimmed *before* the insert,
so the row being written can never be the row the trim removes. `created_at` is set in Python rather
than by the database clock, because this column orders the list: a database clock ties on rows
written close together, and the tiebreaker would then be a random uuid.

**Rate limits.** `POST /search` and `POST /chat` buy a gpt-4o-mini completion per call, on a public
URL. Ten per minute per caller, plus a global daily cap; review writes get sixty per minute. Reads
and thumbnails are not limited — a results grid fetches ten thumbs at once.

**"Caller" is the account when there is one, the address otherwise** *(changed 2026-08-30)*. An
address puts everyone behind one office NAT or VPN egress into a single bucket — ten searches a
minute for a whole building, and a colleague's review pass spending another's allowance. It bit
hardest during the activity the product is for: a review pass *is* a burst of writes, so two
engineers clicking verdicts at a normal pace reached the 60/minute cap together while each stayed
well under it alone. This is not a hole in the bill protection — the per-caller window never was
that. An attacker picks the number of clients either way, by address or by registration, and
`llm_daily_cap` is the ceiling that does not multiply.

| status | when |
|---|---|
| `429` | per-caller rate limit; carries `Retry-After` in seconds |
| `503` | the day's search budget is spent — not a wait-and-retry, tell the operator |

## Errors

| status | when | body |
|---|---|---|
| `422` | request fails validation (empty query, `top_k` out of range) | FastAPI's validation detail |
| `404` | unknown `frame_id` on the thumbnail route | `{"detail": "..."}` |
| `401` | operator endpoint without the token | `{"detail": "..."}` |
| `429` | rate limited | `{"detail": "..."}` + `Retry-After` |
| `503` | artifacts still loading, or the daily cap reached | `{"detail": "..."}` |
| `500` | unexpected | `{"detail": "..."}`, generic on purpose |

`500` bodies never contain a raw exception or stack trace. The rubric asks for "friendly errors that
never leak raw exceptions"; the UI should still have a fallback message rather than printing
`detail` verbatim.

## CORS

Allowed origins come from the `CORS_ORIGINS` env var (comma-separated). **The deployed frontend
origin must be added there or every browser request fails.** Tell the backend owner the Vercel URL
as soon as it exists — including preview deployments if you want those to work.

## Building before the backend is up

Every field above is stable, so the frontend can be built against a fixture. Four states worth
hard-coding, because they are the ones most likely to be forgotten until Demo Day:

1. `matched: true`, `confidence: "high"` — ~10 hits across 5–6 `scene_id`s, `reason: null`
2. `matched: true`, `confidence: "low"` — **the same shape**, plus a `reason`. Results still render;
   the caveat sits above them
3. `matched: false` — `results: []`, `reason` set, empty state
4. `constraint.out_of_scope` set — shape 3 on the served corpus, but the copy is about a limit of
   single-frame search rather than about the archive's contents. On a corpus with source footage it
   is shape 2 instead, with every result carrying a `source`: hard-code both, since which one you
   get is a property of the corpus and not of the query

Real examples to hard-code against, all verified end-to-end:

| query | outcome |
|---|---|
| `a wet road at night` | high |
| `a pedestrian to the front-left` | low |
| `a bus on fire` | no match |
| `a vehicle cutting into our lane` | out of scope |
